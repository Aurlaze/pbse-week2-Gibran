WHAT THIS IS FOR
  A.9 is a condition of passing the assignment. You sign in as an account
  that lacks a right, then send that operation anyway - from the console,
  and by typing the URL. The service must refuse it.

  PASS = the service answers 403 or 404.
  FAIL = the service answers 200. That means the interface was only HIDING
         the control, never refusing it, and no amount of client code fixes
         it. Run this early: if it fails, the backend needs work.

  Total time if nothing goes wrong: about 20 minutes.
  You can do all of this alone. Nothing here needs a teammate.

-------------------------------------------------------------------------------
WARNING - YOUR DATABASE IS SHARED
-------------------------------------------------------------------------------

DATABASE_URL points at the group's Neon database, not localhost. Two things
follow from that:

  * Retiring a court is TERMINAL. There is no operation that brings one
    back. If an attack succeeds against a seeded court, that court is gone
    for everyone, including during the Session 7 demo.
    -> Step 4 below creates a throwaway court to aim at.

  * A teammate rehearsing at the same time will see rows appear and vanish.
    Tell the group before you start, or point DATABASE_URL at a local
    Postgres for the whole exercise.

If something does get retired by accident, re-seeding will NOT fix it -
seed.sql uses ON CONFLICT DO NOTHING, so it skips rows that already exist.
The undo is SQL:

    UPDATE courts SET status='active', is_available=true,
                      retired_at=NULL, retire_reason=NULL
    WHERE status='retired';

    -- crt_93Lm27qR is seeded with is_available=false on purpose:
    UPDATE courts SET is_available=false WHERE id='crt_93Lm27qR';

ATTACK 0 - what is in the token
-------------------------------------------------------------------------------

    __badminton.scopes()

EXPECT: a list WITHOUT courts:write
        e.g. ["courts:read","bookings:read","bookings:write", ...]

If courts:write IS there, the realm is not withholding it by role. Write
that down - it changes what has to be fixed. Continue anyway.

-------------------------------------------------------------------------------
ATTACK 1 - the hidden control, sent anyway
-------------------------------------------------------------------------------

    await __badminton.call("POST", "/courts/crt_a9target/retirement",
      { reason: "from the console" }, { "If-Match": "*" })

EXPECT: status 403
        body type ending in /problems/insufficient-scope

  403 = PASS. The service refused an operation the interface merely hid.
  200 = FAIL CONDITION FOR THE WHOLE ASSIGNMENT. Stop and fix the backend.

RESULT: ______________________________________________________


-------------------------------------------------------------------------------
ATTACK 2 - somebody else's object
-------------------------------------------------------------------------------

bkg_ownedByB is seeded as student-b's booking. You are student-a.

    await __badminton.call("GET", "/bookings/bkg_ownedByB")

EXPECT: status 404

  404 = PASS. "Does not exist" and "not yours" are answered identically, so
        nothing leaks about what other people have.
  403 = FAIL. That tells the attacker the booking is real.
  200 = FAIL. They just read another student's data.

Also read the body: it must not say "you are not allowed to see this
booking". That sentence leaks exactly what the 404 is hiding.

-------------------------------------------------------------------------------
IF ATTACK 1 RETURNS 200
-------------------------------------------------------------------------------

Do not panic and do not patch the client - hiding the button harder changes
nothing, and the grader sends the request from the console.

It means Keycloak issued courts:write to a student, so limiting the client
scope to the administrator role is not enough on its own. The fix is in the
service: the retirement handler must check the caller's role in addition to
the scope, so that a token carrying a scope it should never have been given
is still refused.

That is a backend change of roughly twenty lines plus tests. Bring the
result back to the team before making it - it changes the authorisation
model recorded in docs/decisions/0003-autentikasi.md.
